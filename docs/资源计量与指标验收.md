# 资源计量、基础指标与就绪状态

本次只补第 6 项的这三个部分，继续使用现有免认证 gRPC。不增加监控平台、数据库、告警系统或缓存管理功能。

## 怎么人工验收

在项目目录执行；`--wait` 会等内部服务就绪，避免容器刚启动就运行样例。

```bash
cd /Users/wx/LazyX/sandbox_smokescreen
docker compose up --build -d --wait --wait-timeout 1800
python3 scripts/status.py
python3 scripts/run.py --observability
python3 scripts/status.py
```

专项验收会执行合成任务、准备一个小型 Python 依赖环境、制造构建失败和组件失联，期间服务会重启；结束后恢复原模式。报告保存到代码目录外的 `../sandbox_smokescreen_outputs/compose-<时间>/`。

预期看到全部检查通过，最后查询中：

- `readiness.ready: true`、`reason: "READY"`、`mode: "independent"`。
- 无其他任务时，`accepting_tasks: true`、`inflight: 0`、`cleanup_pending: 0`。
- 构建计数在服务重启后归零，这是进程周期计数的正常行为。缓存镜像数量和保留的任务记录不会因此归零。

验收输出的 `[计量]` 行包含一个任务编号。复制它可查询容器销毁后的用量：

```bash
python3 scripts/status.py --job <任务编号>
```

`--job` 只返回任务元数据，不返回脚本、输入、产物或日志正文。任务记录默认保留 24 小时。验收会重启服务，旧任务可能带有 `RESTARTED_RESULT_UNAVAILABLE`，表示原结果正文不再可取；已保存的用量数字仍可查询。

## 资源数字代表什么

`Status` 和 `Result.status` 增加以下字段，原有调用仍可使用。

| 字段 | 含义 |
|---|---|
| `cpu_usage_usec` | 执行容器累计消耗的 CPU 微秒，除以 1,000,000 得到 CPU 秒；不是任务墙钟时长 |
| `peak_memory_bytes` | 执行容器自创建以来的内核内存峰值，包含子进程；不是配置的内存上限 |
| `cpu_usage_available` / `peak_memory_available` | 是否取得过相应真实计数；为 false 时不要使用对应数值 |
| `resource_sample_unix_ms` | 最近一次成功采集的时间，Unix 毫秒 |
| `resource_usage_final` | 是否在销毁前成功读取了两项计数；运行中或最终读取不全时为 false；是否已完成资源清理仍看 `cleanup_done` |

数据从可信节点的 cgroup v2 `cpu.stat` 和 `memory.peak` 读取，约每个维护周期更新一次，并在销毁前再读。内存峰值由内核累计，因此不依赖采样恰好撞上瞬时分配。字段定义参考 [Linux cgroup v2 文档](https://www.kernel.org/doc/html/latest/admin-guide/cgroup-v2.html)。

**计量范围是整个执行容器**，包含 gVisor、执行组件、输入准备和输出导出开销，不含依赖构建容器或 Smokescreen 代理。最终快照取自销毁前，不包含此后的销毁开销。它适合资源观测，不等同于脚本自身的精确计费值。

取消和执行失败也尽量保留计量；若容器已消失，保留最后成功值，`resource_usage_final` 为 false。故障重启只能恢复已持久化的数字，未采到的用量不会推算。尚未创建容器的任务，以及不支持相应 cgroup 文件的节点，明确返回不可用。

## 基础指标

新增 `Metrics(Empty)` 查询接口。所有数据只包含数量、字节数和固定状态，不附带任务 ID、域名或内容。

| 字段 | 范围 |
|---|---|
| `tasks_by_phase` / `finished_by_outcome` | 当前保留记录按阶段和结果分类；历史过期后减少，不是永久累计 |
| `inflight` / `cleanup_pending` | 未完成任务数；已结束但尚未确认清理的任务或构建数量 |
| `result_cache_bytes` / `history_records` | 当前内存中的结果正文大小；保留的任务元数据条数 |
| `builds_active` / `builds_pending` | 正在构建（含收尾）和等待构建的不同环境数量；相同环境的多个调用方合并计数 |
| `cache_images` / `cache_bytes` | 已登记缓存镜像数和依赖内容大小；不逐次扫描 Docker，外部手工删镜像时可能暂时与实际数量不同；字节数不包含 Docker 所有层的磁盘空间 |
| `environment_counters` | 本次管理进程内的缓存命中、未命中、实际开始构建的成功／失败／取消次数与构建累计毫秒；并发共享一次构建时只计一次构建 |
| `service_started_unix_ms` | 当前管理进程开始时间，用来识别计数重置 |

## 就绪与容量

`Ready` 和 `Metrics.readiness` 使用同一判断。`ready` 表示控制服务、OpenSandbox 与回收器正常，且最近维护周期已通过 Docker 和 OpenSandbox 检查；不是每次查询都重新访问所有组件。维护进展过期或回收器失联时不再就绪。服务尚未监听、退出或挂起时可能直接返回 gRPC 不可达／超时，调用方同样应视为不可用。

`reason` 给出 `READY` 或固定原因，例如 `RESTART_PENDING`、`MANAGER_STALLED`、`OPENSANDBOX_EXITED`、`WATCHDOG_STALE`。`accepting_tasks` 表示此刻是否有容量接收新编号任务；`admission_reason` 给出 `QUEUE_FULL`、`RESULT_CACHE_FULL`、`HISTORY_FULL` 或未就绪原因。空字符串表示没有限制。

**队列满时仍可 `ready: true`，同时 `accepting_tasks: false`。** 这样健康检查不会把正常的容量限制误当故障。就绪是查询时的快照，提交时仍会再次检查；同编号同内容的重复查询式提交不额外占用容量。
